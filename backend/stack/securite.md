# Sécurité et chiffrement : ce qui est retenu

Le RGPD n'impose pas d'algorithme précis (article 32 : mesures appropriées, état de l'art). Le chiffrement symétrique est déjà résistant au quantique : AES-256 garde environ 128 bits de sécurité face à Grover. Le post-quantique ne compte que là où l'on utilise de la clé publique.

| Mesure | Pertinence | Où dans le projet |
|---|---|---|
| **Cascade AES-256-GCM puis XChaCha20-Poly1305** (clé de 512 bits) sur les données personnelles | Oui, retenu : 512 bits de clé réelle avec des algorithmes standards | Champs sensibles en base, pour tous les utilisateurs : nom, prénom, date de naissance, téléphone et adresse postale (§5.4 et §5.7). Un paquet `internal/crypto` avec un format versionné pour pouvoir changer d'algorithme plus tard. Détail dans [Chiffrement des champs](chiffrement.md). |
| **TLS avec échange hybride ML-KEM** (`X25519MLKEM768`) | Oui, gratuit avec une version récente de Go et un navigateur à jour. Protège contre « récolter maintenant, déchiffrer plus tard ». | Navigateur vers Next.js, Next.js vers l'API Go, API vers la base et vers le SMTP. Le composant qui termine le TLS (proxy Docker ou Go) doit être assez récent : à vérifier. |
| **Partage de secret de Shamir** pour la clé maîtresse | Oui, simple et utile | Opérations, pas le code applicatif : la clé maîtresse qui protège les clés de données et les sauvegardes est répartie entre *n* personnes de l'équipe, *k* suffisent pour la reconstituer. |
| **Ed25519** pour des liens signés | Oui, car ils sont de courte durée et le risque quantique est négligeable | Paquet `internal/signedlink`, sans jeton en base, clé dérivée des clés de chiffrement. En service : confirmation d'abonnement à la newsletter, confirmation d'une nouvelle adresse email, lien de désabonnement (§4.2, sans expiration : il doit marcher dans un vieux mail). À venir : lien de notation d'un héros dans le mail de fin d'intervention (§4.3.3 et §6.1.3). Aussi les clés SSH de déploiement. Un identifiant `kid` permet de renouveler la clé. |
| **2FA TOTP** (RFC 6238) | Oui, retenu : un compte modérateur piraté donne accès à tout | Paquet `internal/totp`. Obligatoire pour les modérateurs en production (`HEROS_MFA_MODERATOR_REQUIRED`). Secret chiffré en base, codes de secours à usage unique (seule leur empreinte est stockée), code déjà utilisé refusé (anti-rejeu), faux codes comptés dans le verrouillage progressif. Tant que le code n'est pas saisi, la session est limitée. Aucune route ne désactive la 2FA : un appareil perdu se règle par `make resetmfa`. Détail dans [Sessions](sessions.md). |
| ML-DSA, FHE, MPC, QKD, Threefish | Non, hors de proportion pour ce projet | Non utilisés. Threefish pourra s'ajouter plus tard comme autre id d'algorithme du format versionné. |
